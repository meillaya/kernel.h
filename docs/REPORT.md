# kernel.h — Technical Report

A cross-vendor GPU kernel compiler: a C++23 DSL lowers a kernel through a
structured-SSA custom IR ("atom") into MLIR, then to native code for both
NVIDIA (PTX/cubin, sm_80, cross-compiled) and AMD (AMDGCN ISA/HSACO, gfx1101,
executed locally). This report is the F4 audit target — every number is traced
to a real build/bench artifact in this repo. Artifacts live under
`artifacts/` (generated by `kernelh explore` / `kernelh tune`, gitignored) and
`build/bench/` (`kernelh bench` + `scripts/charts.py`, gitignored); gate
evidence lives under `.omo/evidence/`.

Measured on: **AMD Radeon RX 7800 XT (gfx1101, Navi 32)** — the live local GPU
(full runtime mode, `degraded=false`, see §10). 30 compute units, 16 GiB VRAM
(17163091968 bytes), 64 KiB LDS per workgroup, wavefront size 32.

---

## 1. Overview & architecture

kernel.h compiles one kernel description into both NVIDIA and AMD GPU machine
code, runs it on the local AMD card, verifies the math against an fp64 CPU
reference, and benchmarks it against AMD's own vendor library (rocBLAS). The
compiler is built on MLIR (LLVM 21.1.8) but the front half of the toolchain —
DSL, custom IR, the seven passes — is intentionally MLIR-free and sits on its
own tiny IR.

```
                        ┌────────────────────────────────────────────┐
                        │  C++23 DSL (include/kernelh/dsl)           │
                        │  program().tile(32,32,32).map_blocks()     │
                        │  .map_warps().use_shared_memory()          │
                        │  .kernel("gemm").shape({m,n,k}).emit()     │
                        └──────────────┬─────────────────────────────┘
                                       │ emit()

   ┌───────────────────────────────────────────────────────────────────┐
   │  atom IR — custom structured SSA (lib/ir)                         │

   │  canonicalize → cse → fuse → tile → promote-shared → vectorize   │

Two compile entry points, both in-process (no shell-out):

  dialect registered.
- `kernelh` (tools/kernelh) — the production CLI. Subcommands `compile`,

Reproduction: `devenv shell -- bash -c 'cd $KERNELH_ROOT && build'` then run
any `./build/tools/kernelh/kernelh <subcommand>` command in this report.

## 2. IR design

### 2.1 Structured SSA rationale (decision D10)

The atom IR is **structured SSA** — nested block scopes with values dominating
within their scope, and **no arbitrary gotos or phis**. Control flow is
restricted to `atom.loop_for ... iter_args() -> (...)`, which is both a
structured loop and the only SSA merge point (loop-carried values are the
loop's iter_args, terminated by `atom.yield`). `atom.reduce` (sum/max over a
tensor dim) is built on `loop_for` + iter_args.

Rationale:

- **Reductions are first-class.** Softmax's running-max/running-sum, GEMM's
  accumulator, scan's carry, and attention's online statistics are all
  loop-carried iter_args — representable without converting to/from a
  generic CFG. The pass pipeline (fusion in particular) inspects loop domains
  and barriers; a structured form makes "same iteration domain, no barrier in
  between" a local syntactic check instead of a global analysis.
- **The verifier is cheap and loud.** Dominance, barrier placement, operand
  types, and shared-memory totals are structural properties. The verifier
  reports every violation in one pass (`verifyModule` collects all
  Diagnostics, never early-exits), which the round-trip self-check in
  `kernelh explore` relies on (§3).
- **Round-trip text.** `.atom` is both printer output and parser input; a
  stable, deterministic value-numbering scheme (MLIR-style active-name set —
  nested scopes never shadow a live outer name) makes every per-pass dump
  re-parseable and verifiable.

### 2.2 Op inventory (pinned, Metis G2 / plan item 9)

Types: `f16`, `f32`, `i32`, `i64`, `index` scalars; `tensor<...xE, space>`
where `space ∈ {global, shared}`; `vector<WxE>`. Ops are plain data
(`enum class OpKind` in `include/kernelh/ir/ops.hpp`):

| kind | purpose |
| --- | --- |
| `atom.const` | scalar constant (int or float payload) |
| `atom.add/sub/mul/div/fma/max/min` | scalar/vector arithmetic |
| `atom.cmp` + `atom.select` | comparison (result i32 carrier) + select |
| `atom.math{exp,log,sqrt,rsqrt,tanh}` | math intrinsics |
| `atom.load` / `atom.store` | tensor load/store with affine index expressions |
| `atom.load_vec` / `atom.store_vec` | width-attribute vector memory ops |
| `atom.alloc_shared` | static shared memory, size from type (G9) |
| `atom.barrier` | workgroup barrier (top level of loop bodies only) |
| `atom.thread_id / block_id / block_dim / grid_dim {dim}` | launch intrinsics |
| `atom.loop_for` | structured loop with iter_args + `atom.yield` |
| `atom.reduce` | sum/max over a tensor dim (built on loop_for) |
| `atom.copy` | tile copy helper (global→shared staging) |
| `atom.kernel` | container with schedule attrs (`tile`, `map_blocks`, `map_warps`, `use_shared_memory`, `vector_width`, `unroll`, `shape`) |

### 2.3 `.atom` syntax — real example from a real compile

This is the verbatim pre-pipeline input of the GEMM explore run
(`artifacts/run-report-amd/00-input.atom`, emitted by
`kernelh explore --kernel gemm --shape m=256,n=256,k=256 --target
amdgcn-gfx1101`). It is the tiled shared-memory GEMM (plan item 26 fix, §8.3): a
flat 2048-f32 LDS buffer holds per-wavefront A row-slices and the B tile; the
k-tile loop carries the f32 accumulator as an iter_arg.

```
atom.kernel @gemm(%v0: tensor<256x256xf32, global>, %v1: tensor<256x256xf32, global>, %v2: tensor<256x256xf32, global>) {
  tile = [32, 32, 32]
  map_blocks = true
  map_warps = true
  use_shared_memory = true
  vector_width = 1
  unroll = 1
  shape = {k = 256, m = 256, n = 256}
  %v3 = atom.const 0 : index
  ...
  %v15 = atom.thread_id x : index
  %v16 = atom.block_dim x : index
  %v17 = atom.div %v15, %v12 : index
  %v18 = atom.mul %v17, %v9 : index
  %v19 = atom.mul %v17, %v12 : index
  %v20 = atom.sub %v15, %v19 : index
  %v21 = atom.alloc_shared : tensor<2048xf32, shared>
  atom.loop_for %v3 to %v4 step %v7 iter_args() -> () {
    ^bb0(%v22: index):
      ...
      %v28 = atom.loop_for %v3 to %v6 step %v9 iter_args(%v14) -> (f32) {
        ^bb0(%v29: index, %v30: f32):
          %v31 = atom.sub %v6, %v29 : index
          %v32 = atom.min %v9, %v31 : index
          atom.loop_for %v20 to %v32 step %v12 iter_args() -> () {
            ^bb0(%v33: index):
              %v34 = atom.add %v29, %v33 : index
              %v35 = atom.load %v0[%v22, %v34] : tensor<256x256xf32, global>
              %v36 = atom.add %v18, %v33 : index
              atom.store %v35, %v21[%v36] : tensor<2048xf32, shared>
              atom.yield
          }
          ...
          atom.barrier
          %v33 = atom.loop_for %v3 to %v32 step %v7 iter_args(%v30) -> (f32) {
            ^bb0(%v34: index, %v35: f32):
              %v36 = atom.add %v18, %v34 : index
              %v37 = atom.load %v21[%v36] : tensor<2048xf32, shared>
              ...
              %v42 = atom.fma %v37, %v41, %v35 : f32
              atom.yield %v42 : f32
          }
          atom.barrier
          atom.yield %v33 : f32
      }
      atom.store %v28, %v2[%v22, %v27] : tensor<256x256xf32, global>
      atom.yield
  }
}
```

(Schedule attrs are printed in a fixed order; `shape` is key-sorted; float
constants round-trip shortest — `atom.const 0 : f32`.)

## 3. Pass pipeline

Canonical order (pinned by `kernelh::passes::defaultPipelineOrder()` in
`lib/passes/pipeline.cpp`, Metis G3 — the pipeline-order lock tests prove the
order is load-bearing):

```
canonicalize → cse → fuse → tile → promote-shared → vectorize → unroll
```

Every pass is a self-registering `.cpp` in `lib/passes/` (GLOB + a file-scope
static initializer; consumers force-load the archive with
`$<LINK_LIBRARY:WHOLE_ARCHIVE,kernelh_passes>`). `kernelh explore` runs this
exact pipeline and dumps `00-input.atom` + `01-<pass>.atom` … `07-unroll.atom`,
then **re-parses and re-verifies every dump in-process** (fail-loud corruption
probe). Real before/after excerpts from `artifacts/run-report-amd/`:

### 3.1 canonicalize (01) — before vs after

GEMM's pre-pipeline input already has no foldable constants (all `atom.const`s
are leaves), so `01-canonicalize.atom` == `00-input.atom` (constant folding,
identity elision, dead-op elimination found nothing to do — the dumps are
byte-identical). The fusion example below shows a case where canonicalize
*did* rewrite: `x + 0.0` identity elision is exactly what lets the vectorizer
widen the fused chain (§3.3 in learnings).

### 3.2 cse (02) — before vs after

`02-cse.atom` (3258 B) < `00-input.atom` (3461 B): CSE merged duplicate
constants. In the input, `%v8 = atom.const 32` and `%v9 = atom.const 32`
(different SSA ids, same value) plus duplicate `1024`/`1024` — CSE
value-numbered them down to one each, and every use rewrote to the survivor.

### 3.3 tile (04) — before vs after

The domain loop `atom.loop_for %v3 to %v4 step %v7` (`0..256 step 1`) is
rewritten into a block/tile loop. After the pass (`04-tile.atom`) the kernel
body starts with `atom.block_id x`, and the domain loop becomes:

```
  %v16 = atom.block_id x : index
  %v17 = atom.const 32 : index
  %v18 = atom.mul %v16, %v17 : index          ; base = block_id * 32
  ...
  atom.loop_for %v3 to %v28 step %v5 iter_args() -> () {
    ^bb0(%v29: index):
      %v30 = atom.mul %v29, %v25 : index
      %v31 = atom.add %v30, %v21 : index      ; row = i*W + wf
      %v32 = atom.add %v18, %v31 : index      ; gi = base + row
      %v33 = atom.cmp lt %v31, %v17 : index   ; ok_tile guard
      ...
```

with the tile guard (`select(ok, gi, 0)`) wrapping exactly the A-load and the
C-store — the only two uses of the induction `i`. (GEMM's `04` == `05`/`06`/`07`
because promote-shared is a no-op on the pre-staged template — every global
load feeds only a shared store — and vector_width=1/unroll=1 leave the IR
unchanged; that idempotency is itself asserted by the explore self-check.)

### 3.4 fuse — real before/after from `artifacts/run-report-fused/`

The fused_gelu kernel is the fusion proof (`kernelh explore --kernel
fused_gelu --shape n=1048576 --target amdgcn-gfx1101`). **Before** (02-cse.atom,
two same-domain loops + an intermediate `tensor<1048576xf32>` staging buffer):

```
  atom.loop_for %v15 to %v3 step %v16 iter_args() -> () {
    ^bb0(%v17: index):
      %v18 = atom.load %v0[%v17] : tensor<1048576xf32, global>
      %v19 = atom.fma %v4, %v18, %v5 : f32
      atom.store %v19, %v1[%v17] : tensor<1048576xf32, global>
      atom.yield
  }
  atom.loop_for %v14 to %v3 step %v15 iter_args() -> () {
    ^bb0(%v16: index):
      %v17 = atom.load %v1[%v16] : tensor<1048576xf32, global>
      %v18 = atom.mul %v17, %v17 : f32
      %v19 = atom.mul %v18, %v17 : f32
      ... tanh ... 
      atom.store %v27, %v2[%v16] : tensor<1048576xf32, global>
      atom.yield
  }
```

**After** (03-fuse.atom) — ONE loop computes the whole chain pointwise and the
intermediate buffer disappears (the producer store + consumer load are gone):

```
  atom.loop_for %v14 to %v3 step %v15 iter_args() -> () {
    ^bb0(%v16: index):
      %v17 = atom.load %v0[%v16] : tensor<1048576xf32, global>
      %v18 = atom.fma %v4, %v17, %v5 : f32
      %v19 = atom.mul %v18, %v18 : f32
      %v20 = atom.mul %v19, %v18 : f32
      %v21 = atom.mul %v8, %v20 : f32
      %v22 = atom.add %v18, %v21 : f32
      %v23 = atom.mul %v7, %v22 : f32
      %v24 = atom.math tanh %v23 : f32
      %v25 = atom.add %v24, %v6 : f32
      %v26 = atom.mul %v5, %v18 : f32
      %v27 = atom.mul %v26, %v25 : f32
      atom.store %v27, %v2[%v16] : tensor<1048576xf32, global>
      atom.yield
  }
```

(Fusion fires only on same-domain producer/consumer pairs with no barrier in
between — the barrier-separated negative fixture in `test/fixtures/
chain_barrier.atom` is left unchanged by design.)

## 4. MLIR lowering

Dialect chain, all in `lib/compiler/emitter.cpp` (two stages):

```
atom IR ──(lowerToAtomDialect)──▶ atom dialect (tblgen, §2.2 ops as MLIR ops)
         ──(lowerAtomToGpu)────▶ gpu.module { memref.global addrspace-3,
                                              gpu.func with dynamic memref args,
                                              scf.for / vector / arith / math }
         ──(fuse + canonicalize + cse cleanup)──▶ emitGpuModule
```

**Device-only decision and rationale (pinned in the plan):** the emitter
produces a `gpu.module` with `gpu.func` kernels and NO `gpu.launch`, NO
outlining, and NO `gpu-to-llvm` host machinery. The kernels are launched by
kernel.h's own thin runtime (§6) directly at the device-ABI level — there is no
host-side generated launcher, no mgpu/MLIR ExecutionEngine dependency. The
device module is exactly what the vendor serializers consume
(`gpu-module-to-binary`), and the descriptor ABI (§6) is what the runtime
builds launch arguments for. This keeps the runtime and the compiler
decoupled: the runtime links no MLIR at all.

Real MLIR output (verbatim from `artifacts/run-report-nv/gpu.mlir` — the
vecadd gpu.module, identical shape on the AMD side):

```
module {
  gpu.module @kernelh {
    gpu.func @vecadd(%arg0: memref<?xf32>, %arg1: memref<?xf32>, %arg2: memref<?xf32>) attributes {kernel} {
      %c1024 = arith.constant 1024 : index
      %block_id_x = gpu.block_id  x
      %block_dim_x = gpu.block_dim  x
      %grid_dim_x = gpu.grid_dim  x
      %thread_id_x = gpu.thread_id  x
      %0 = arith.muli %block_id_x, %block_dim_x : index
      %1 = arith.addi %0, %thread_id_x : index
      %2 = arith.muli %block_dim_x, %grid_dim_x : index
      scf.for %arg3 = %1 to %c1024 step %2 {
        %3 = memref.load %arg0[%arg3] : memref<?xf32>
        %4 = memref.load %arg1[%arg3] : memref<?xf32>
        %5 = arith.addf %3, %4 : f32
        memref.store %5, %arg2[%arg3] : memref<?xf32>
      }
      gpu.return
    }
  }
}
```

Static shared memory is the addrspace-3 global mechanism, **not** a per-thread
`alloca` (Oracle B4 — NVPTX treats `alloca addrspace(3)` as per-thread, which
would silently break cross-thread exchange). Real GEMM shared buffer from
`artifacts/run-report-amd/rocdl.mlir`:

```
  gpu.module @kernelh [#rocdl.target<chip = "gfx1101">] attributes {llvm.data_layout = ...} {
    llvm.mlir.global external @gemm_shared_0() {addr_space = 3 : i32} : !llvm.array<2048 x f32> {
      %0 = llvm.mlir.undef : !llvm.array<2048 x f32>
      llvm.return %0 : !llvm.array<2048 x f32>
    }
    llvm.func @gemm(%arg0: !llvm.ptr, %arg1: !llvm.ptr, %arg2: i64, ... ) attributes {gpu.kernel, rocdl.kernel} {
      ...
```

Key lowering facts (verified in `.omo/notepads/atomgpu/learnings.md` plan items 20/21):

- Kernel args are **dynamic-shape memref descriptors** (`memref<?xf32>`,
  `memref<?x?xf32>`), never bare pointers — the descriptor ABI (Oracle B3;
  bare-ptr requires static shapes). A rank-N buffer expands to
  `2*N+3` argument slots: allocated ptr, aligned ptr, offset i64, N sizes,
  N strides (§6).
- Loop bounds for dynamic args come from `memref.dim` at runtime, not the
  static atom type.
- `atom.reduce` lowers to nested `scf.for` + iter_args; `atom.copy` to nested
  `scf.for` + memref loads/stores.
- Custom cmp (i32 carrier) → `arith.extui`; select → `arith.trunci` —
  canonicalize folds `trunci(extui(cmp))` back to a plain `cmpf` + select.
- The emitter's literal `kernel` marker attr is normalized to `gpu.kernel`
  inside the backend shim (`normalizeKernelMarkers`) so NVPTX/ROCDL emit
  `.visible .entry` / proper kernels.

Two vendor paths in `lib/compiler/backends.cpp`; each consumes a *fresh clone*

	.reg .b32 	%r<8>;
	.reg .b64 	%rd<22>;

	ld.param.b64 	%rd12, [vecadd_param_1];

	mov.u32 	%r2, %ntid.x;
	mov.u32 	%r4, %tid.x;

	setp.gt.u64 	%p1, %rd20, 1023;

	...
$L__BB0_2:
	add.s64 	%rd17, %rd1, %rd21;
	ld.global.b32 	%r5, [%rd17];
	add.s64 	%rd18, %rd2, %rd21;
	ld.global.b32 	%r6, [%rd18];

	add.s64 	%rd19, %rd3, %rd21;

### 5.3 Serialization mechanics (toolkit aggregates + external ld.lld)

`gpu-module-to-binary` never touches a GPU; it runs vendor linkers. The exact
mechanisms (verified in the smoke gates, plan items 7/8, and learnings):

- **ROCDL `format=bin`** (HSACO): the serializer requires the ROCm toolkit —
  `<toolkit>/llvm/bin/ld.lld` (an **external** linker, LLD 22.0.0
  rocm-7.2.3) plus the device-libs at `<toolkit>/amdgcn/bitcode/` (`ocml.bc`,
  `ockl.bc`, `hip.bc`, `opencl.bc` + 67 `oclc_*` control bitcodes; 71 files
  total — see mlir/lib/Target/LLVM/ROCDL/Target.cpp in llvm-project, which
  hard-requires these paths). The `rocm-toolkit-root` **linkFarm aggregate**
  (devenv.nix, plan item 3) remaps
  `${rocmPackages.llvm.lld}/bin/ld.lld → llvm/bin/ld.lld` and every
  `${rocmPackages.rocm-device-libs}/amdgcn/bitcode/*.bc → amdgcn/bitcode/`.
  Toolkit is wired via `ROCM_TOOLKIT_ROOT`
  (`/nix/store/6lh8nfk56a662jf87d1l1xddq6fi5bf1-rocm-toolkit-root`). A bogus
  toolkit path fails cleanly with the serializer's own error (`ROCm amdgcn
  bitcode path: ... does not exist`), and `format=isa` still requires the
  toolkit because the serializer drives the same ld.lld path.
- **NVVM `format=bin`** (cubin): needs `ptxas` (CUDA 12.9,
  `Build cuda_12.9.r12.9/compiler.36037853_0`) and libdevice
  (`nvvm/libdevice/libdevice.10.bc`, passed via the pass's **own** `l=`
  linkFiles option — never inside `opts=`), both from the `cuda-toolkit-root`
  aggregate (`/nix/store/bwrf6gq7mg7cq596hacd3qdr78z24g2f-cuda-toolkit-root`).
  `format=isa` (PTX text) needs no toolkit.
- Valid format strings are `offloading|llvm|assembly|isa|binary|bin|
  fatbinary|fatbin` — the plan pins "asm" as invalid (Oracle B1), and the
  codebase never uses it.
- Blob extraction: after `gpu-module-to-binary` the module holds
  `gpu.binary [#gpu.object<target, bin = "...">]`; `compileToBlob` walks for
  the `BinaryOp`, matches the object's `CompilationTarget`, and reads the raw
  payload StringAttr (in-memory it is raw bytes, MLIR escaping is print-time
  only). Verified artifacts start with the ELF magic `7f 45 4c 46`; cubin
  `llvm-readobj -h` reports `Machine: EM_CUDA (0xBE)`.
- `kernelh-opt --compile-target=<...>` exposes the same pipelines for
  hand-authored fixtures; `kernelh compile` / `kernelh explore` drive them
  in-process for the production kernels.

Real artifact bytes: `gemm.hsaco` 6528 B (ELF, 3 amdhsa note sections),
`gemm.isa` 14877 B, `vecadd.cubin` 3496 B (EM_CUDA), `vecadd.ptx` 1619 B.

## 6. Runtime & loading

Thin, plain-C++ runtime (`lib/runtime`, linked with clang + `-lamdhip64`, no
hipcc; HIP type-free headers). Live path on this box:

- `DeviceContext::create` → `hipSetDevice(0)` + live queries (device name
  "AMD Radeon RX 7800 XT", 30 CUs, 64 KiB LDS, wavefront 32, max threads 1024 —
  all agree with the gfx1101 device-limits table entry).
- `GpuModule::load(image, size)` → **`hipModuleLoadData`** → `get_function`
  → **`hipModuleGetFunction`** → `KernelLaunch.launch(fn)` →
  **`hipModuleLaunchKernel`** with `sharedMemBytes=0` (static LDS only, the
  v1 ABI rule) and the descriptor-packed `kernelParams`.
- **Descriptor ABI** (Oracle B3, byte-verified): each rank-N buffer packs
  `[allocated_ptr, aligned_ptr, offset=i64(0), size_0..size_{N-1},
  stride_0..stride_{N-1}]` — 5 slots for a 1-D buffer, 11 for rank-2. Strides
  are emitted dim-0-first (16×8 → strides `[8,1]`). Scalars follow by value.
  `LaunchArgs::params()` returns the `void**` array pointing at each slot.
- `EventTimer`: HIP events (`hipEventCreate/Record/ElapsedTime/Destroy`) —
  warmup 5, median of 20 in the bench harness.
- `KernelLaunch::launch` runs the plan item 32 launch verifier before every
  submission (threads ≤ max, grid dims ≤ limits, static shared ≤ LDS, and
  occupancy > 0 via the analytic fallback — the HIP occupancy API returns
  `hipErrorInvalidDeviceFunction` for every kernel on this ROCm 7.2.3 +
  CachyOS-kernel combo, §10).

**CUDA backend (cross-ready, never linked):** the same interface is
implemented over the CUDA Driver API bound at runtime via
`dlopen("libcuda.so.1")` + `dlsym` of 24 symbols (cuInit, cuDeviceGet,
cuModuleLoadData, cuModuleGetFunction, cuLaunchKernel, cuEvent*,
cuMemAlloc_v2/cuMemFree_v2/cuMemcpyHtoD_v2/cuMemcpyDtoH_v2, …). If dlopen
fails every call returns a clean error (`kCudaDriverUnavailable`), and
`kernelh bench` on NVIDIA targets exits 77 (skip). `ldd` on the binary shows
zero libcuda references. **Live-hardware validated on an RTX 6000 Ada pod**
(§10): the full production path — DSL → pipeline → emitter → NVVM cubin →
descriptor-ABI launch → numeric verification — runs on real NVIDIA hardware.

Smoke-gate loading evidence: the plan item 7 MLIR-emitted `xchg.hsaco` (10208 B,
cross-thread LDS exchange kernel) loads and executes via the production
descriptor-ABI kernel — `LOAD-MODULE-PASS` 2/2, host-side full-array numeric
verification (out[i] == (i+1)%256).

## 7. Autotuning

`kernelh tune` (plan plan item 34, `lib/compiler/autotuner.cpp` + the CLI driver
in `tools/kernelh/main.cpp`). GEMM-only in v1.

**Config space** (`gemm_config_space()`): 216 = 3(bm) × 3(bn) × 2(bk) ×
2(waves) × 2(unroll) × 3(vec) with bm/bn ∈ {64,128,256}, bk ∈ {16,32},
waves ∈ {4,8}, unroll ∈ {1,2}, vec ∈ {1,2,4}. `--max-candidates` caps the
number evaluated; `--sample` sizes the fixed-seed random sample; `--refine-
budget` bounds best-neighbor refinement.

**Evaluation gates, in order, in a forked child with a wall-clock deadline:**

1. Compile for the tuning shape; an LDS/shared-memory compile error is
   surfaced as `pruned: lds`.
2. plan-item 32 launch verification → `pruned: launch`.
3. plan-item 33 resource check (resources.json on the actual artifact) → `pruned:
   vgpr` / `pruned: lds` if the kernel cannot be resident (the
   profiler-feedback seam).
4. **Mandatory numeric re-verification** on a small shape (≤128/dim) against
   the fp64 reference, tolerance rel-Frobenius ≤ 1e-5. Any candidate that
   fails is discarded — the plan rule "no candidate accepted without numeric
   re-verification".
5. EventTimer timing (warmup 3, median 10) on the tuning shape for accepted
   candidates.

**Cache:** whole-run JSON cache (`build/tune-cache.json`, hand-rolled JSON
writer) keyed `sha256(kernel+shape+device_name)`. A second run with the same
key is served entirely from cache.

**Real run — `artifacts/tune-report/tune-results.csv`** (verbatim, 8
candidates at `m=512,n=512,k=512`, `--max-candidates 8`):

```
kernel,shape,bm,bn,bk,waves,unroll,vec,ms_median,accepted,reason
gemm,"k=512,m=512,n=512",64,64,16,4,1,2,0,false,reverify: FAIL (rel-frobenius 0.7071607398 > 1e-5)
gemm,"k=512,m=512,n=512",128,128,16,8,1,1,0,false,reverify: FAIL (rel-frobenius 0.8660254038 > 1e-5)
gemm,"k=512,m=512,n=512",128,64,32,8,2,4,0,false,reverify: FAIL (rel-frobenius 0.8837545775 > 1e-5)
gemm,"k=512,m=512,n=512",256,64,32,8,1,2,0,false,reverify: FAIL (rel-frobenius 0.7072175998 > 1e-5)
gemm,"k=512,m=512,n=512",128,256,16,8,2,1,0,false,reverify: FAIL (rel-frobenius 0.9703290074 > 1e-5)
gemm,"k=512,m=512,n=512",256,128,32,8,1,2,0,false,reverify: FAIL (rel-frobenius 0.8660397367 > 1e-5)
gemm,"k=512,m=512,n=512",64,256,32,4,1,4,0,false,reverify: FAIL (rel-frobenius 0.8660456794 > 1e-5)

This is a **real, honest negative result** — and a real finding. The autotuner
caught a genuine correctness bug: **the unroll=2 GEMM configurations fail
numeric re-verification** (candidates 2, 4, 7; rel-Frobenius 0.883–0.970). The
root cause is documented in `.omo/notepads/atomgpu/problems.md`: the unroll
pass's partial-unroll cleanup loop mis-remaps the k-loop iter_args carry
chain, corrupting the accumulator. The autotuner's mandatory re-verification
**prunes those configs** exactly as designed — no wrong kernel ever gets
accepted, and the search ends with `no accepted candidate; skipping refinement`
rather than shipping a broken config. The full run logs the same story:
`cache-miss` on the first run, `cache-hit` + `tune ok (served from cache)` on
the re-run, and `best config: none (no candidate passed all gates)`.

| shape (m=n=k) | kernelh ms | kernelh GFLOPS | rocBLAS ms | rocBLAS GFLOPS | ratio |
| --- | ---: | ---: | ---: | ---: | ---: |

![gemm](../build/bench/charts/gemm_gflops_vs_size.png)

**Honest gap, no parity claim:** kernel.h's GEMM is a scalar, tiled,
static-shared-memory kernel (f32 FMA, no tensor cores, no WMMA — see §9). At
8192³ it is **~9.5× slower than rocBLAS** (1072.5 vs 10196.5 GFLOPS); the gap
is largest at small sizes (17.8× at 512³) where rocBLAS's highly-tuned
inner-kernel and launch overhead dominate. The relative gap narrows as N grows
(tile efficiency improves; the 8192³ kernelh run is the single slowest cell in
the suite at 1025 ms), but even the best kernelh cell (1275.5 GFLOPS at 4096³)
reaches only ~8% of the measured fma ceiling (15559.8 GFLOPS). Root causes:
scalar (non-vectorized) accumulation with a 32×32×32 tile that leaves the
GPU's VGPR/FMA throughput under-utilized at 12.5% occupancy (see table below),
no double-buffering/pipelining, and only ~30% of peak LDS bandwidth exploited
by the ds_load_2addr pattern. rocBLAS runs WMMA-free too on gfx1101 but uses
register-blocked accumulation, wider tiles, and aggressive pipelining — all
v1 scope-outs here.

**Honest analysis:**

- **fused_gelu** is close to (and at 2^22 faster than) the HIP references —
  the fusion pass (§3.4) eliminates the intermediate tensor's global
  round-trip. Its 1100 GB/s exceeds the 347.8 GB/s triad ceiling because the
  triad microbenchmark streams 3 GiB (DRAM-bound) while fused_gelu's 16 MiB
  working set rides the GPU's L1/L2 caches — a real observation: the roofline
  triad ceiling is a DRAM ceiling, and small working sets legitimately sit
  above it.
- **softmax/layernorm are the honest weak spot**: 8.5–69 GB/s vs 400–700 for
  the HIP references — a 10–80× gap. These are bandwidth-bound kernels where
  the compiler-optimized reference uses float4 vectorization, whereas the
  kernelh templates run scalar (vector_width=1 in the default schedule). This
  is a real, measured inefficiency of the v1 codegen, not noise.
- **scan** is near-parity (3.16–3.57 vs 3.68–4.35 GB/s) — the two-pass
  Blelloch cost shows up as the flat low rate, and both implementations are
  bandwidth-bound the same way.

  cuBLAS/CUTLASS rows skip with exit 77 on this box — no NVIDIA driver). The
  online, tiled, fp32 attention reaches ~43.6 GFLOPS at seq=1024 (AI = s/4 =
  256 flops/byte, well into the compute region of the roofline; the achieved
  point sits far below the fma ceiling — it is a small-work, low-occupancy
  kernel at 3.125% occupancy, §8.4).

one — documented, not papered over.

## 9. Limitations

1. **No WMMA / MFMA / tensor-core instructions** — scope OUT by the plan. The
   reason is a real correctness concern on this GPU generation: gfx1101 WMMA
   is untrusted upstream (ROCm/ROCm#6349); the plan greps kernels/lib for
   wmma/mfma and requires zero hits. GEMM and attention therefore run on
   scalar f32 FMAs, which caps them far below the vendor libraries (§8.2).
2. **NVIDIA is cross-compile-only on this box** — no NVIDIA hardware locally;
   everything NVIDIA-side is emitted, blobs verified (ELF/PTX magic,
   `.target sm_80`, `Machine: EM_CUDA`), and exercised on a rented **RTX 6000
   Ada pod** (validation evidence in `.omo/evidence/
   nvidia-rtx6000-validation-kernelh.txt` — full production path runs and
   numerically verifies there: `NV-VECADD-PASS`). `kernelh bench` NVIDIA rows
   exit 77 locally (no CUDA driver).
3. **Unofficial distro/kernel** — the host is a rolling distro with an
   in-tree AMD driver/kernel combination (the plan item 2 draft's VERIFY-LANE-A
   residual-risk note). It is smoke-gated and works (§10), but it is not an
   officially supported driver stack, and the HIP occupancy API is broken on
   it (hipErrorInvalidDeviceFunction) — the analytic occupancy fallback is
   the working path.
4. **Static shared memory only in v1** — `sharedMemBytes=0` at launch and
   addrspace-3 module globals; no dynamic shared memory (avoids the hidden
   kernel-argument ABI). This pins the LDS budget at compile time (attention
   already sits at 33024/65536 B).
5. **No double-buffering / pipelining** in the v1 GEMM — one k-tile staged,
   barrier, compute, barrier; the GPU's memory pipeline is idle during the
   compute phase. This is the single biggest GEMM performance lever left on
   the table (plan scope-out).
6. **No `hipMallocAsync`** (ROCm/ROCm#6178 in-tree driver regression) —
   plain `hipMalloc` only; no stream-ordered allocation.
7. **Occupancy API unavailable on the local stack** — measured occupancy is
   analytic-only (§8.4).
8. **rocprofv3 is not packaged here** — the resource reporter falls back to
   `llvm-readobj --notes` on the HSACO and `ptxas -v` for the NVIDIA side
   (§5.3, plan item 33).

## 11. Future work

Prioritized by measured impact (§8 evidence):

1. **Fix the unroll-pass iter_args corruption** (`.omo/notepads/atomgpu/
   problems.md`) — the autotuner's numeric gate currently rejects every
   unroll=2 GEMM config. Fixing the main/cleanup-loop remap tables unlocks the
   unroll dimension of the autotune space.
2. **GEMM performance** (9.5× gap, §8.2): double-buffered k-tile pipelining
   (v1 scope-out), register-blocked accumulation to cut the 41-VGPR footprint
   and lift occupancy off 12.5%, and a wider tile (BM/BN > 32) with proper
   bank-conflict-free layouts. Target: close the gap toward rocBLAS's ~10.2
   TFLOPS while staying WMMA-free.
3. **Vectorize the bandwidth-bound kernels** (softmax/layernorm 10–80× gap,
   §8.3): the vectorize pass exists but the default schedules carry
   vector_width=1; enabling float4 loads/stores on the elementwise kernels is
   the highest-leverage codegen change measured.
4. **Attention** (43.6 GFLOPS, 3.125% occupancy): shrink the 33024 B
   K/V/Q staging footprint (smaller per-block tiles, or register-resident
   segments) to admit more than one block per CU; add a real cross-vendor
   baseline by running the existing cuBLAS/CUTLASS cross harness on NVIDIA
   hardware.
5. **WMMA/MFMA** — explicitly deferred until ROCm/ROCm#6349 is resolved
   upstream; re-audit gfx1101 correctness before enabling tensor cores.
6. **Autotuner widening**: add a non-uniform sampling strategy (the current
   space's unroll=2 corner is entirely dead), persist per-config timing for
   accepted configs (the CSV already carries the schema), and add
   softmax/attention to the tunable kernel set.
7. **Occupancy measurement** on a supported driver stack (the local ROCm +
   rolling-kernel combo returns hipErrorInvalidDeviceFunction) to replace the
   analytic-only measured column with real API numbers.
8. **NVIDIA execution locally** — when NVIDIA hardware is available, run the
   full kernelh suite's cuda-cross rows instead of exit-77 skips.
9. **Docs polish** (`README.md`, quickstart) as plan plan item 40.
